# PostgreSQL database design

This is a design specification, not an applied schema or migration. [README](../README.md) contains the eleven-table ER diagram. All UUIDs are generated by the application or PostgreSQL when implemented; all timestamps use `timestamptz` and default to database time. Fields are `NOT NULL` unless marked nullable. Price uses `numeric(12,2)`, not floating point. Names and labels are trimmed on input; nonblank checks use `btrim(value) <> ''`. Update timestamps are changed explicitly in the same transaction as the row edit.

The current identity of a stock line is case-insensitive `(make, model)` among active rows. The `model` value must include enough variant detail to distinguish different stock lines. If the product later tracks year or trim separately, add those columns and revise the identity index before importing such rows. There is no VIN, persisted availability status, payment, or reservation.

## Data dictionary and relationships

Every foreign key below uses `ON DELETE RESTRICT` (or PostgreSQL's equivalent `NO ACTION`) unless a different action is stated. History is retained; users, categories, vehicles, purchases, and receipts are not casually physically deleted. Application operations named below are planned, not implemented.

### `users`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `full_name` | `text`, nonblank |
| `email` | `text`, nonblank; unique on `lower(email)` |
| `password_hash` | `text`, nonblank; encoded salted hash only |
| `role` | `text` default `user`, check in (`user`, `admin`) |
| `is_verified`, `is_active` | `boolean` default `false`, `true` respectively |
| `created_at`, `updated_at` | `timestamptz` |

One user may record many stock receipts, save many vehicles, make many purchases, receive many notifications, and own zero or one cart. All those child foreign keys restrict physical user deletion. Registration creates an active `user` and supplies no role from the request; only an out-of-band administrator action may grant `admin`. Login reads the hash and active flag. Verification is a future account flag, not a claim that email verification is implemented; initial accounts can log in while unverified until a verification workflow is designed.

### `vehicle_categories`

| Column | Type and rule |
|---|---|
| `id` | `integer GENERATED ... AS IDENTITY` primary key |
| `name` | `text`, nonblank; unique on `lower(name)` |

One category (Sedan, SUV, Hatchback, Coupe, Pickup, Van) classifies zero or many vehicles; `vehicles.category_id` references it and restricts physical deletion while used. Normalising categories prevents inconsistent free-text spellings and supports a reliable search join. Admin catalogue management selects a category; category seeding/maintenance will be defined with implementation.

### `vehicles`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `make`, `model` | `text`, each nonblank; model includes variant if needed |
| `category_id` | `integer` FK to `vehicle_categories.id` |
| `price` | `numeric(12,2)`, check `>= 0` |
| `quantity` | `integer` default `0`, check `>= 0` |
| `low_stock_threshold` | `integer` default `3`, check `>= 0` |
| `created_at`, `updated_at` | `timestamptz` |
| `deleted_at` | nullable `timestamptz`; NULL is active |

One vehicle has zero or many images, receipts, favourites, cart items, historical purchase items, and notifications. The referencing FKs restrict physical deletion; admin DELETE instead sets `deleted_at`. The active `(lower(make), lower(model))` combination is unique. `price` is current catalogue price; purchase items keep history. Availability is derived from `deleted_at IS NULL AND quantity > 0`. Admin create may set opening inventory through the designated workflow; ordinary edit cannot directly change quantity. Purchases and restocks change quantity only inside their transactions. A zero-stock row remains visible; a deleted row cannot be newly selected, purchased, or restocked.

### `vehicle_images`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `vehicle_id` | `uuid` FK to `vehicles.id` |
| `url` | `text`, nonblank approved image reference |
| `alt_text` | `text`, nonblank accessible description |
| `display_order` | `integer`, check `>= 0`; unique with `vehicle_id` |
| `created_at` | `timestamptz` |

Each image belongs to exactly one vehicle, and a vehicle has zero or many images. The FK restricts physical vehicle deletion. Admin image operations insert, edit, reorder, or remove rows. Store references rather than binaries to keep catalogue queries and backups small; the smallest `display_order` is the cover image. Reordering multiple positions needs a transaction that avoids transient uniqueness conflicts.

### `stock_receipts`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `vehicle_id` | `uuid` FK to `vehicles.id` |
| `actor_id` | `uuid` FK to `users.id`; application requires admin |
| `kind` | `text`, check in (`opening`, `restock`) |
| `quantity_added` | `integer`, check `> 0` |
| `request_id` | nullable `uuid` only for `opening`; required for `restock` |
| `created_at` | `timestamptz` |

One vehicle has zero or many receipts and one admin may record many receipts. Both FKs restrict physical deletion. A positive opening quantity creates one `opening` receipt in the vehicle-create transaction; zero opening quantity needs no receipt. A partial unique index allows at most one opening receipt per vehicle. Restock inserts a `restock` receipt and increments stock in one transaction. Unique `(actor_id, request_id)` for restocks makes a successful retry safe; the application also compares its original vehicle and quantity so reuse of a key for different input is rejected. Receipts are immutable audit history.

### `favourites`

| Column | Type and rule |
|---|---|
| `user_id` | `uuid` FK to `users.id`, part of composite PK |
| `vehicle_id` | `uuid` FK to `vehicles.id`, part of composite PK |
| `notify_on_restock` | `boolean` default `false` |
| `created_at` | `timestamptz` |

This is the user–vehicle many-to-many bridge: users save many vehicles; a vehicle can be saved by many users. Composite PK forbids duplicates. Both FKs restrict physical parent deletion. Users may add/remove their own favourite and change its opt-in flag, even when stock is zero. These actions do not change stock; removing a favourite ends future alerts but leaves already-created notifications intact.

### `carts`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `user_id` | `uuid` FK to `users.id`, unique |
| `created_at`, `updated_at` | `timestamptz` |

A user has zero or one reusable cart; every cart has exactly one owner. The FK restricts physical user deletion. The application lazily creates a cart on first add and updates its timestamp when items change. Checkout empties purchased items but retains the cart.

### `cart_items`

| Column | Type and rule |
|---|---|
| `cart_id` | `uuid` FK to `carts.id`, part of composite PK |
| `vehicle_id` | `uuid` FK to `vehicles.id`, part of composite PK |
| `added_at` | `timestamptz` |

This cart–vehicle many-to-many bridge contains zero or many vehicles per cart; a vehicle may be in many carts. Both FKs restrict parent physical deletion. One row means intent to buy **one** unit, so there is no quantity or stored price. Adding the same item again is idempotent. New adds require an active, in-stock vehicle, but existing items remain visible if later unavailable. Add/remove/clear operations never reserve or reduce stock. A cart read joins current vehicle price and stock.

### `purchases`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `user_id` | `uuid` FK to `users.id` |
| `source` | `text`, check in (`direct`, `cart`) |
| `request_id` | `uuid`, unique with `user_id` |
| `total_price` | `numeric(12,2)`, check `>= 0` |
| `purchased_at` | `timestamptz` |

One user makes zero or many purchases; each completed purchase groups one or more items. User deletion is restricted. The header records who bought, how, when, and the total. Direct purchase creates one item; cart checkout creates one item per selected vehicle. The unique user/request pair prevents another completed purchase on retry. The application rejects key reuse with a different source or item set. `total_price` equals the sum of item `unit_price` values; this cross-table invariant and nonempty item set are validated before transaction commit, not by a row `CHECK`. Completed purchase rows are immutable.

### `purchase_items`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `purchase_id` | `uuid` FK to `purchases.id` |
| `vehicle_id` | `uuid` FK to `vehicles.id` |
| `vehicle_label` | `text`, nonblank snapshot of make and model/variant |
| `unit_price` | `numeric(12,2)`, check `>= 0` |

The historical purchase–vehicle bridge gives each purchase one or more items and allows a vehicle to appear in many purchases. Unique `(purchase_id, vehicle_id)` implements the one-unit-per-vehicle cart rule. Both FKs restrict physical deletion. The direct-purchase or checkout transaction inserts these immutable rows. Snapshots preserve what the buyer saw when the sale committed, even if the current vehicle label or price changes later. Each row counts as one unit in reconciliation.

### `notifications`

| Column | Type and rule |
|---|---|
| `id` | `uuid` primary key |
| `recipient_id` | `uuid` FK to `users.id` |
| `vehicle_id` | nullable `uuid` FK to `vehicles.id` |
| `type` | `text`, check in (`low_stock`, `out_of_stock`, `back_in_stock`) |
| `event_key` | `text`, nonblank stable server-generated operation/event identifier |
| `message` | `text`, nonblank snapshot |
| `created_at` | `timestamptz` |
| `read_at` | nullable `timestamptz` |

One user receives zero or many notifications; a vehicle may be linked to zero or many notifications, and a notification may omit a vehicle. The FKs restrict physical deletion of referenced users/vehicles. Stock-changing transactions insert one row per selected recipient; `(recipient_id, type, event_key)` is unique so retry cannot duplicate a message. Only the authenticated recipient can list or mark their own rows read. These are in-app records, not email/push delivery.

## Indexes and constraints

PostgreSQL primary keys and unique constraints create their own indexes. Foreign keys do **not** automatically index the referencing column; the explicit indexes below serve named queries. Avoid adding speculative indexes before real query plans justify them.

| Rule or index | Why |
|---|---|
| PK on every entity and composite PK on `favourites(user_id, vehicle_id)`, `cart_items(cart_id, vehicle_id)` | Identity and duplicate prevention |
| FKs listed above, all restrictive | Valid relationships without deleting history |
| Unique expression index `users(lower(email))` | Reject case variants of the same address; lookup at login |
| Unique expression index `vehicle_categories(lower(name))` | Prevent duplicate body styles |
| Partial unique index `vehicles(lower(make), lower(model)) WHERE deleted_at IS NULL` | One active stock line for the chosen identity |
| Index `vehicles(category_id, price) WHERE deleted_at IS NULL` | Active category/price filtering; make/model text search may need separate indexes after query measurement |
| Unique `vehicle_images(vehicle_id, display_order)` | Stable ordered gallery and cover lookup |
| Partial unique `stock_receipts(vehicle_id) WHERE kind = 'opening'` | At most one opening event per vehicle |
| Partial unique `stock_receipts(actor_id, request_id) WHERE kind = 'restock'` | Restock retry safety |
| Unique `carts(user_id)` | One reusable cart per user |
| Unique `purchases(user_id, request_id)` | Direct purchase and checkout retry safety |
| Unique `purchase_items(purchase_id, vehicle_id)` | One unit of a vehicle per purchase |
| Index `purchase_items(vehicle_id)` | Vehicle sales history and reconciliation |
| Index `stock_receipts(vehicle_id)` | Vehicle receipt history and reconciliation; opening partial index alone cannot serve all receipts |
| Index `notifications(recipient_id, created_at DESC)` | Recipient inbox in newest-first order |
| Unique `notifications(recipient_id, type, event_key)` | One notification per recipient and event |

Checks also enforce nonblank text (`btrim`), positive receipt quantity, nonnegative `price`, `unit_price`, `total_price`, `quantity`, `low_stock_threshold`, and `display_order`, allowed role/source/type/kind values, and `request_id IS NOT NULL` for restocks. The `uuid` request keys are supplied once by the caller per intended operation. PostgreSQL can enforce those row rules; it cannot use a simple `CHECK` for inventory reconciliation, purchase-total equality, purchase nonemptiness, role authorisation, or the recipient selection rules. Those need server validation and transactions.

## Inventory transactions

**Opening inventory:** admin creates a vehicle. Set its starting quantity to zero, then if requested opening quantity is positive, add exactly one opening receipt and set the vehicle quantity in the same transaction. No receipt is created for zero. Ordinary vehicle updates cannot change quantity. Initial stock is thus explainable from receipts.

**Direct purchase:** look up a prior `purchases` row by authenticated user and request ID; return that result if the same request already succeeded. Otherwise begin a transaction, lock the target vehicle row (or atomically decrement with an active/positive-stock condition), recheck active and positive stock, insert a `direct` purchase header and one item snapshot, decrement quantity by one, fan out eligible stock notifications, and commit. If any step fails, roll back. A uniqueness race on the request key resolves by reading the already committed result, never by decrementing again.

**Restock:** require admin, a positive quantity, and a request ID. Return an earlier matching receipt for a retry; reject a reused key with different input. In a transaction lock the active vehicle, add quantity, insert a `restock` receipt, and create back-in-stock notifications if old stock was zero and new stock is positive. Commit together. Do not allow a normal listing edit to change quantity.

**Cart checkout:** the cart never reserves stock. The user confirms the latest item prices in the checkout request. Look up a prior purchase by user/request ID first. In one transaction lock the user's cart and items, then lock vehicle rows in ascending ID order. Reject empty carts. Recheck active status, positive stock, and each confirmed price. On any mismatch, roll back and return a conflict response with the refreshed cart; buy nothing. Otherwise insert one `cart` header and one snapshot item per vehicle, set header total to the exact sum, decrement each quantity by one, insert applicable alerts, remove bought cart items, and commit. Row locks serialize competing buyers; stable lock order reduces deadlocks. On successful retry return the original purchase without changing stock or cart again. All-or-nothing checkout prevents surprise partial orders.

For each vehicle, reconcile `vehicles.quantity = COALESCE(SUM(stock_receipts.quantity_added), 0) - COUNT(purchase_items.id)`. Each item is one completed unit. Favourites and cart items never enter this equation. A reconciliation query can report mismatches; transaction tests must verify the live quantity remains consistent with history.

## Notification rules

| Event | Transition | Recipients |
|---|---|---|
| `low_stock` | Old quantity above configured threshold; new quantity positive and at/below it | Active admins |
| `out_of_stock` | Positive to zero | Active admins |
| `back_in_stock` | Restock from zero to positive | Active users with that vehicle favourited and `notify_on_restock = true` |

Notifications use a stable key derived from the stock-changing operation and event. A retry must reuse the same key; the unique recipient/type/event constraint suppresses duplicates. Low stock and out of stock are separate thresholds; a threshold of zero cannot produce a positive low-stock event. Users whose cart contains a vehicle are not automatically subscribed. Read and mark-read queries always filter by authenticated `recipient_id`.

## Deletion policy

Admin vehicle deletion sets `deleted_at`, preserving receipts and purchase history. It does not erase existing cart items; those show the listing as unavailable and block checkout until removed. A category used by a vehicle cannot be physically deleted without reclassification. Purchases, purchase items, and receipts are immutable and cannot be cascaded away. User physical deletion is restricted while dependent records exist; an account can instead be deactivated with `is_active = false`. Explicit favourite/cart-item/image deletion is allowed as part of normal user/admin operations. No cascading parent deletion is required for the current design.

## Open decisions before implementation

The backend uses Node.js/TypeScript with Express and `pg`; initial migrations exist for `users`, `vehicle_categories`, and `vehicles` in `migrations/001_create_users_categories_vehicles.sql`. Registration and login are implemented; unverified active accounts may log in because email verification still has no workflow. The active make/model identity assumes the model label includes any meaningful variant; separate year or trim fields would require a revised uniqueness rule.
